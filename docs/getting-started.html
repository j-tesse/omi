Omi, on your own server

Where do your words go when you wear an Omi?

Normally: through half a dozen cloud services. This repo is about bringing them home — here's how it all fits together, and how to drive it.

Scroll ↓

First: what is Omi?

A pendant that listens, and a backend that remembers

Omi is an open-source wearable. A small pendant records what you hear and say all day.

The audio becomes conversations (transcripts + summaries), memories (facts about you) and a chat you can ask questions.

Key idea The pendant is dumb. All the smarts live in the backend — and the backend is what we're running locally.
The pendant captures audio and streams it over Bluetooth. It does no processing.
The phone app forwards the audio stream over a WebSocket to the backend.
The backend (in upstream/omi/backend/) orchestrates everything else.
Speech-to-text turns audio into timestamped text segments, live.
An LLM reads the transcript and writes summaries, extracts memories, answers chat.
Upstream, the last four boxes are cloud services ☁ — Deepgram, OpenAI, Firebase, Google Cloud…
This repo's goal: run every one of them on this server 🏠. Your audio never leaves the house.

The one big constraint

The GPU is taken

0

The RTX 5090's memory is held by the existing vLLM container running Gemma 31B — that's our local LLM, at localhost:8000/v1.

Decision vLLM keeps the GPU. Everything else — speech-to-text included — runs on the 12-core Ryzen CPU.

Why the LLM is tricky

Upstream hard-codes model names

Every backend feature asks for gpt-6-luna or gpt-5-nano by name — there's no setting to change it.

The fix: llm-proxy, a tiny pass-through that rewrites the model field and forwards everything else untouched.

Why a proxy? Renaming inside vLLM would mean changing the shared vLLM container. A plain pass-through also keeps tool calls and structured output working.

Embeddings

Turning text into meaning-numbers

An embedding is a list of numbers that describes what a text means. Similar meaning gives similar numbers, even across languages:

"I'm hungry" ↔ "Ich habe Hunger"
0.92
"I'm hungry" ↔ unrelated sentence
0.32

The embed service runs BGE-M3 on the CPU and works with English and German.

Heads-up BGE-M3 vectors have 1024 numbers, OpenAI's have 3072. That's fine while vector search is off, but switching EMBED_MODEL later means re-indexing.

Auth + database

Firebase, without Google

Omi keeps users, conversations and memories in Firestore. Google ships an emulator of it, a local stand-in that needs no account, and the backend supports it out of the box.

8103Firestore
8104Auth
8105Web UI

Open the UI at localhost:8105 (over an SSH tunnel for 8103–8106 if you're remote) to browse the data.

Data survives only a clean stop It's saved to state/firebase/export/ on docker compose stop/down/restart. A crash or kill loses everything since the last clean stop.

Speech-to-text

The stt service

A small CPU-only web server in services/stt/. It speaks exactly the same protocol as upstream's self-hosted Parakeet service.

Why that matters The Omi backend can use it with zero code changes — just two env vars:
STT_SERVICE_MODELS=parakeet HOSTED_PARAKEET_API_URL=http://stt:8000

How live transcription works

From audio stream to sentence

The app sends raw PCM16 audio to WS /v3/stream, a chunk at a time.
A VAD (voice activity detector) marks which chunks contain speech, and the service buffers them.
When speech stops for 0.7 s (STT_STREAM_HANGOVER_S), the utterance is over.
The engine transcribes just that clip and sends back a segment JSON. Long monologues are force-cut at 15 s.

Batch files go to POST /v1/transcribe or /v2/transcribe instead — same engine, whole file at once.

Hands on

Run it in four commands

  1. Configure. Every variable is documented inside.
    cp .env.example .env
  2. Start everything. First boot downloads models to .cache/models/.
    docker compose up -d --build
  3. Smoke-test each service: one script each.
    scripts/test_stt.sh scripts/test_llm_proxy.sh scripts/test_embed.sh scripts/test_firebase.sh
  4. Watch the logs.
    docker compose logs -f stt llm-proxy embed firebase

Common tweaks

Swap the engine

# in .env STT_ENGINE=whisper # apply docker compose up -d stt

Test with your own audio

scripts/test_stt.sh my.wav 1

The 1 streams at real speed, like a real pendant.

Benchmark accuracy in noise

NOISE=pink SNRS="clean 10 0" \ REFERENCE="what was said" \ scripts/bench_stt.sh my.wav

Results land in results/bench_stt/ with word error rates.

Check embeddings via the proxy

scripts/test_embed.sh http://127.0.0.1:8101

Check that Firebase data survives a restart

scripts/test_firebase.sh --persist

Wipe the Firebase data

docker compose stop firebase rm -rf state/firebase/export

Find your way

The repo, folder by folder

Tap to open.

  • The living source of truth: hardware, ports, decisions, status. Read it first; keep it updated.
  • app/main.py endpoints · engines.py the models · pipeline.py VAD + chunking · stream.py live sessions. New engine = subclass Engine.
  • One file, app/main.py. Aliases come from LLM_MODEL_ALIASES in .env; a *=target entry catches every unlisted name.
  • OpenAI-style /v1/embeddings server. It also accepts the token-ID arrays and base64 output that the upstream clients use, which off-the-shelf servers don't.
  • firebase.json sets the ports; change them there and in compose. Rules and indexes are mounted from upstream/omi/, not copied.
  • A test_*.sh per service, plus bench_stt.sh. Persisted scripts are preferred over one-off commands.
  • The real Omi code as a git submodule (git submodule update --init). Never edit it — configure it from outside.
  • Models, sample audio, benchmark output, and Firebase's saved data. All git-ignored.
